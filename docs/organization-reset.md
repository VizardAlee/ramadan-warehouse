# Administrator start-fresh reset

This is a tenant-generation reset, not a Firestore deletion. The active system administrator opens **Administration → Start fresh**, reviews the current record counts, reconciles every offline POS device, enters an audit reason, types `RESET <organization code>`, and confirms. A sign-in within the previous 15 minutes is required. No reset runs merely by visiting the page.

Before the first mutation, the trusted App Check-protected callable requires a READY managed Firestore backup of `(default)` with a snapshot from the preceding 24 hours and more than 24 hours of remaining retention. The callable's service account needs permission to list backups; failure to verify blocks the reset. The selected backup name and snapshot time are recorded with the reset. In the local emulator, this external backup gate is bypassed and marked as emulator-only.

The callable then marks the old organization `resetting`, creates a new `preparing` organization with the same legal identity, deactivates and disables every other user, clears their location assignments, and then atomically archives the old organization and activates the new one. The initiating administrator retains access. The old organization ID remains on its immutable inventory, sales, purchasing, accounting, and audit records. No historical ledger entry, sale, invoice, customer, supplier, or audit document is deleted. A reset record links the old and new organization IDs and records the reason, initiator, timestamps, and former user assignments. A retry with the same idempotency key resumes a partial reset.

An archived organization is not operationally accessible through the current app. Historical recovery or review requires an authorized administrative procedure against the archived organization ID. Managed Firestore backups remain independent and should be verified before a real-world reset. Seven-day backup retention is not a substitute for an indefinite legal archive; the Firestore archive must be retained under the organization's record-retention policy.

After completion, refresh the app and set up the new Head Office/store, products, opening stock, financial accounts, customers, suppliers, and prices. Reactivate individual users in **Administration → Users** only after assigning the appropriate new locations. Do not reuse the old organization ID in new transactions. Previously queued offline POS sales cannot be replayed into the new organization because their old branch, shift, and stock references are not valid there. Confirm tills are synchronized before proceeding; outstanding offline drafts remain on the local device for reconciliation but are not imported by the reset.

If the callable stops while the old organization is `resetting`, retry from the same browser and confirmation phrase; do not create a second reset request. The existing idempotency key is retained locally until the callable reports completion. If the browser state is lost, an operator must inspect `organizationResets` and resume the exact operation ID; do not manually delete or switch organization documents. A user-profile/Auth mismatch after a partial execution also requires operator review, not direct Firestore editing.

This reset preserves, but does not automatically export, old records to a separate bucket or prove a restore at reset time. Backup metadata verification is not a restore drill. It does not delete Firebase Auth accounts, managed backups, Functions, rules, App Hosting, uploaded files, or cloud resources. The separate synthetic production-conversion reset script is not part of this workflow and must not be used here.
